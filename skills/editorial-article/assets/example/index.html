One memory for several agents

We separated project memory from individual chat histories, so different agents can retrieve the same notes and check their sources.

A project decision, an updated specification or a test result may be needed in several tools. Brain makes a shared collection of notes available through . The client saves selected information and retrieves relevant context for the next task.

  • Savebrain_push accepts a note and queues it for processing.
  • Findbrain_pull searches for passages related to a question.
  • Checkbrain_open opens the full document referenced in a result.

The client decides what to save and when to retrieve memory. The server does not automatically capture every conversation or data from every application.

When saving a decision, include the reasoning behind it. A note saying "we chose SQLite" records the outcome. Adding the RAM constraint and deployment setup lets another agent check whether that choice still fits the project.

How a note enters memory

The agent calls brain_push. The server validates the content, writes the note to the inbox and adds it to the queue. Accepting a note does not require the model to respond. More expensive processing is handled later by a background .

The worker splits the text into , computes embeddings and asks the model to suggest a folder, tags and facts. It then updates the file and its index. Each record has an identifier, source and metadata. allows a request to be retried with the same request_id without creating another note.

A failure partway through processing should not erase accepted content. The recovery mechanism finds files whose index needs updating. The queue also uses a time-limited lease so an old worker cannot finish a job that another worker has already claimed.

Matching meaning

Vectors help retrieve similar content even when the question uses different words.

embedding / sqlite-vec

finds words and phrases. turns text into a vector so search can compare the meaning of the question and stored passages. The algorithm merges both lists. A then scores the selected candidates against the question again.

A result includes a passage, the document path, status and trust information. If a match is weak, the server can mark it as low_confidence. This also tells the agent not to treat that material as a firm basis for an answer.

This is where comes in: the model answers using retrieved context. brain_pull returns results that the client model can use, while brain_answer also provides an answer-generation path inside Brain. Sources remain available for checking.

What graph connections mean

Search results answer a specific question. The graph helps you explore a project: documents in the same folder, explicit links between notes or similar content. In the Brain panel, selecting a node opens its document.

Read the edges carefully. Sharing a folder is an organizational relationship; vector similarity means related text. Neither one proves causation. Current search retrieves document passages. Displaying a graph does not automatically turn it into .

Fact status and access boundaries

A model can extract a useful fact from a note. It can also misinterpret the text. Records therefore carry a status and source, rather than treating all information equally.

capturedproposedconfirmed

A saved note, a proposed fact and a confirmed fact. Notes and facts have their own statuses; not every record goes through every stage.

The worker marks model-generated conclusions as proposed. An authorized person can confirm or correct a fact. The current code also has a nightly dreamprocess: it organizes memory and can promote a recurring fact when it appears in at least two sources and is not marked as contradictory. This checks consistency between records. A mistake repeated twice can still be a mistake.

Access and approvals are separate decisions. A role determines which memory tools a client can use; policy decides which actions need approval. The HUMAN role provides administrative operations, so its credentials need particular care.

Note content is material to read. A document saying "ignore earlier rules" does not become an instruction to the agent. Separating data from instructions is part of this project’s MCP contract.

Ways to connect to Brain

We kept MCP as the common interface. The transport can change depending on where the client and server run, while the tools for saving and retrieving memory stay the same.

Local process / stdio
The client starts Brain on the same computer and communicates through the process’s input and output streams. Access follows the operating-system account running it.
Local or remote HTTP
A client connects using Streamable HTTP. This can be a service on the same computer or a server on another machine. Remote access needs an encrypted connection and authentication.
A custom application
An application can use an MCP client SDK or an adapter that calls the same tools. A separate REST API would be another interface to build, not an existing part of this setup.
Reading the files
Markdown notes remain readable in an editor without an MCP client. This gives access to the files, not to the server’s retrieval, queue or approval tools.

On one computer or on a VM

A local setup keeps the server, notes and index on your computer. Models can run locally if the machine has enough resources, or use a configured external service. Keeping the files local does not automatically make every operation offline.

Our setup puts the Brain service on a virtual machine. Several clients can use that shared memory without moving the vault between computers. Models can run on the VM or on another machine. A VM changes where the service runs; it does not provide access control by itself.

Access to memory needs its own protection

The HTTP server checks a bearer token before allowing access to its MCP tools. That token identifies a role; the role and policy decide what the client may do. An encrypted connection protects data in transit, while authentication decides who gets access.

For remote use, keep access inside a private network where possible, or expose it through HTTPS with authentication. Credentials belong in the client’s secure configuration, never in a public article, page source or shared link.

The current integration uses configured tokens. Individual client credentials, revocation and rotation are further security work. A full OAuth 2.1 sign-in flow is an option for compatible remote clients, not a feature claimed as already implemented here.

Queues, performance and limitations

This also affects response time. A write through brain_push goes into the queue, while a direct edit through brain_note_write refreshes the index and may compute embeddings. A large import and a short question have very different costs. The CPU embedder gives queries priority between successive document chunks.

Frequently asked questions

Does Brain become "smarter" by itself?

The collection of stored information grows, its organization improves and more context becomes available. These operations do not change the language model’s weights. Answer quality still depends on the notes, retrieval and the model using them.

Can every program use it?

A program needs an MCP client or an adapter that calls the server’s tools. Having a server does not automatically connect every application. The client also decides when to save an important finding and when to search for earlier knowledge.

What remains available if the model stops responding?

Markdown files remain available. An accepted note stays in the INBOX and queue, and keyword search can work without vectors. Sorting and answer generation require a working model. Each function has different dependencies.
